## Trampa nueva y pagada: OpenCode rechaza leer el brief fuera de `--dir`

La primera corrida murió a los 9,8 s con
`permission requested: external_directory (...\tools\qa\*); auto-rejecting` — el
brief estaba en el repo y el snapshot en un directorio temporal fuera de él, así que
OpenCode lo trató como directorio externo y se auto-rechazó. En PBI-006 no pasó
porque el snapshot vivía **dentro** del repo (`qa/snapshot-pbi006`), y brief y
snapshot compartían raíz.

**Arreglo aplicado:** copiar el brief adentro del snapshot (`BRIEF-QA.md.prompt`) y
apuntar `-BriefPath` ahí. Corrida buena: 98,8 s, exit 0. Es mejor que la solución de
PBI-006, que de hecho le daba a QA acceso de lectura a todo el repo vivo en vez de
sólo al snapshot.

## Trampa nueva y pagada: `git archive | tar` no sirve desde PowerShell con rutas de Windows

`git archive d90fb73 | & tar -x -C $snap` falló con
`/usr/bin/tar: C\:\\Users\...: Cannot open: No such file or directory`: el `tar` de
MSYS destroza la ruta de Windows que le pasa PowerShell. El traspaso de fase 0-1 lo
daba por funcionando, y funciona con rutas cortas dentro del repo, no con una ruta
absoluta con `\` afuera.

**Arreglo:** `git archive --format=zip -o <zip> <commit>` + `Expand-Archive`. Sin
dependencias de MSYS, sin traducción de rutas.

### Y la misma trampa estaba latente en `Invoke-SonarGate.ps1`

No era sólo del snapshot de QA: `tools/sonarqube/Invoke-SonarGate.ps1` armaba su
propio snapshot con el mismo `git archive HEAD | & tar -x -C $snapshotDir`, y murió
igual en el paso 4/8. **Había funcionado los 12 análisis anteriores por casualidad**:
en esta máquina hay dos `tar` en el PATH —

```
C:\Program Files\Git\usr\bin\tar.exe     (MSYS, traduce rutas)
C:\WINDOWS\system32\tar.exe              (bsdtar, no traduce)
```

— y cuál gana depende del orden del PATH de la consola desde la que se lo llame. Con
el de System32 adelante andaba; con el de Git adelante, no. Una herramienta que anda
o no según de dónde la llamés no es confiable aunque tenga 12 corridas verdes.

Corregido con el mismo patrón zip, más el comentario que explica por qué. Gate
re-corrido sobre el commit `e685e1e`: **OK**, 38/38 tests, evidencia en
`C:\IA\Data\sonarqube\reports\tokmd\20260925-110449\`.

## PBI-008, primera mitad: cablear `--verify` en `cli.py` (bloqueo #1 resuelto)

Retomado con luz verde de Fabián ("dale, arrancá con --verify"), después de validar
las dos precondiciones:

- **La key de `anthropic.api-key` en la bóveda DPAPI (`multi-modelos-ai`) autentica de
  verdad**: `GET /v1/models` devolvió 12 modelos.
- **Y tiene facturación habilitada**: probar el endpoint exacto que usa `--verify`
  (`POST /v1/messages/count_tokens`) con contenido válido y un modelo real
  (`claude-sonnet-5`) respondió `input_tokens=8` de punta a punta — auth, billing y
  conteo, sin gastar en generación (es un endpoint de conteo, no de completar).

Seguido el orden de ADR-006: firma vacía en `cli.py` (`--verify` como flag, la rama
`if verify:` sólo con `raise NotImplementedError`) → spec para TDD
(`tools/deepseek/specs/PBI-008-verify.md.prompt`) → DeepSeek escribió
`tests/test_cli_verify.py` (5 tests, $0.0017, 5.6s) → **rojo confirmado** (4/5
fallando exactamente por el `NotImplementedError` del stub) → implementado →
**verde**, 43/43 con la suite completa.

Diseño: `--verify` sólo vale si el tokenizer resuelto es Claude (si no, `UsageError`
limpio, sin traceback). Usa `--model` como id real de la API si se pasó (por ejemplo
con `--platform opencode --model claude-opus-5`), si no, `claude-sonnet-5` por
default — independiente de `--claude-family`, que nombra versiones propias de `ctok`
("3.0", "4.7", "4.8"), no ids reales de la API. `get_client`/`measure_frame`/
`count_verified` se importan por nombre en `cli.py` (no el módulo) para que los tests
puedan mockearlos con `monkeypatch.setattr("tokmd.cli.<nombre>", ...)` sin key real ni
red — mismo patrón que ya usaban los tests de `verify.py`.

## BUG-001: `measure_frame` mandaba un espacio en blanco, la API real lo rechaza

Encontrado por Desarrollo, no por QA — haciendo la prueba de humo real de `--verify`
contra la API (con `anthropic` instalado vía `uv sync --extra verify`, que no viene
por defecto). Primera corrida:

```
anthropic.BadRequestError: Error code: 400 - ... 'messages: text content blocks must
contain non-whitespace text'
```

`measure_frame` llama con `content=" "` — un solo espacio, diseño original de la spec
de TDD de PBI-006. La API real lo rechaza; el cliente falso de los tests de PBI-006
nunca lo hubiera detectado porque no valida contenido, sólo mira si es igual a `" "` o
no. **El PASSED 4/4 de QA de PBI-006 sigue siendo correcto para lo que probó** (la
aritmética de `count_verified`), pero nadie había llamado al endpoint real hasta hoy.

Corregido: `" "` → `"."` en `verify.py`, con el fake de `test_verify.py` actualizado
para reconocer el nuevo contenido mínimo (ambos cambios comentados citando el bug).
Re-verificado con la misma prueba de humo real: responde `input_tokens` correcto, y
`tokmd smoke.md --platform claude-code --verify` completo imprime la tabla con
números reales. Documentado en detalle en
`docs/bugs/BUG-001-espacio-en-blanco-rechazado-por-count-tokens.md`, con nota cruzada
en el cierre de PBI-006.
